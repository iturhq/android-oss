All E2E use cases are listed below.
Each use case covers a single user scenario and specifies preconditions, steps, expected results, and the UI identifiers required for test implementation.

== Conventions

* *Test account:* any registered Google account.
* *Test activity ID:* `AAAABBBBCCCCDDDDEEEE` (20-char alphanumeric, satisfies `IturActivityId` validation).
* *Invalid activity ID:* `ZZZZZZZZZZZZZZZZZZZZ` (does not correspond to an existing activity).

== Executable coverage

The demo-flavor instrumented suite implements these IDs through the real
`MapScreen`/`MapViewModel` Hilt graph. Compose Test drives application UI;
UIAutomator is restricted to the Android-owned permission dialog in UC-01
and UC-02. Scenario repositories replace network services deterministically,
and the hosted emulator runs the suite on every change.

UC-07 is reconciled with the current accepted UX: anonymous users see
*Sign in*, while *Start an activity* is offered only after sign-in. UC-19
tests the canonical one-shot, idempotent attention request from
`UC-ACTIVITY-005`; cancellation is not part of that contract. UC-22's
organiser acknowledgement controls remain deliberately deferred: the
canonical system use case says organiser-facing UI is future work, so the
Android boundary scenario verifies that pending backend state is preserved
and no participant-only hail action leaks into the organiser UI.
