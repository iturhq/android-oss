== Context

The repository already enforces one static-analysis concern -- formatting --
via Spotless (`ktlint` for Kotlin, plus license-header checks for
`.kt`/`.kts`/`.xml`), applied through the `spotless/spotless.gradle.kts` init
script and run in CI (`spotlessCheck`). Nothing enforced deeper static
analysis: code smells, complexity, unused/dead constructs beyond what
`ktlint` catches, or Android/Kotlin-specific anti-patterns. `AOSS-35C2`'s
dead-code sweep and `AOSS-CA86`'s commented-code sweep were both manual,
one-time efforts rather than a standing, automated check.

== Decision

Add https://detekt.dev[Detekt] as the project's static-analysis tool,
alongside Spotless rather than replacing it:

* Spotless/`ktlint` continues to own formatting and license headers.
* Detekt owns code-smell, complexity, and structural analysis, using its
  default rule sets (`buildUponDefaultConfig = true`) with no rules
  disabled or weakened.
* Detekt's own `formatting` rule set is **not** applied, since it would
  duplicate/conflict with `ktlint`'s existing formatting enforcement --
  the two tools' job is deliberately non-overlapping.
* Applied uniformly to every subproject via the root `build.gradle.kts`
  `subprojects {}` block (mirroring how JVM target and Android
  `compileOptions` are already applied there), so newly added modules pick
  it up automatically rather than needing per-module opt-in.
* Config lives at `config/detekt/detekt.yml` (generated via
  `detektGenerateConfig`, i.e. the full default rule set made explicit and
  versioned rather than hand-trimmed).
* `./gradlew detekt` runs in CI (`.github/workflows/ci.yml`) alongside
  `spotlessCheck`, as its own step so the two failure modes (formatting vs.
  code smell) stay distinguishable in CI output.

=== Baseline for existing code

This is an existing, previously-unanalyzed codebase, not a greenfield one.
Running Detekt's default rule set cold surfaced real findings in several
modules (61 in `feature:map`, 122 in `core:ui`, smaller counts elsewhere;
four modules -- `core:auth`, `core:location`, `core:data-api`, `core:model`
-- had zero). Two options existed for that debt: disable/relax the rules
that fire on existing code, or grandfather the existing findings via
Detekt's baseline mechanism (`detekt-baseline.xml` per module, generated by
`detektBaseline`) and hold only new code to the full standard. This ADR
chooses the baseline: it keeps the rule set at full strength for everything
written from this point forward without requiring an unrelated, disruptive
mass-refactor of every flagged file as a prerequisite for adopting the
tool. Each module's `detekt-baseline.xml` is committed, so growing it back
open (a new violation landing in an already-baselined file) is visible in
review as a diff to that file, and shrinking it (fixing a baselined smell)
is a deliberate, reviewable removal.

== Rationale

. **Additive, not overlapping.** Spotless/`ktlint` and Detekt check
  different things; running both is standard practice in the Kotlin
  ecosystem specifically because neither subsumes the other.
. **Default rules, not a custom-curated subset.** Hand-picking which
  Detekt rules to enable invites quietly dropping inconvenient ones over
  time with no record of why. Baselining existing findings instead keeps
  the rule set itself honest while still making the tool adoptable today.
. **Repository-wide via `subprojects {}`, not per-module.** The module
  graph is actively changing (`core:data` was mid-split into
  `core:data-api`/`core:data-firebase`/`core:data-fake` while this task was
  in flight); a per-module opt-in list would silently miss newly added
  modules.

== Consequences

* Positive: every module now has a standing, automated code-quality check
  beyond formatting, enforced in CI.
* Positive: no existing file had to be touched to adopt this -- the
  baseline mechanism means introducing the tool and paying down existing
  debt are two separate, independently schedulable pieces of work.
* Neutral: the four already-clean modules (`core:auth`, `core:location`,
  `core:data-api`, `core:model`) have no `detekt-baseline.xml` file at all,
  since Detekt does not write one when there is nothing to baseline; a
  `detekt-baseline.xml` reappearing in one of those modules later is
  itself a meaningful signal that new debt was baselined rather than fixed.
* Negative: `feature:map` and `core:ui` in particular carry a non-trivial
  amount of grandfathered debt (61 and 122 findings respectively) that
  Detekt will not flag again unless it regresses further. Paying that down
  is out of scope for this task and is left for whoever next works
  substantially in those modules to reduce opportunistically, not a
  dedicated follow-up task by itself.

== Alternatives considered

=== Detekt with rules disabled/relaxed to pass cleanly on existing code

[cols="1,4"]
|===
| Criterion | Assessment

| Strengths
a|
* No baseline file bookkeeping
* A clean `./gradlew detekt` run with no suppressed history

| Weaknesses
a|
* Silently weakens the standard actually being enforced, with no
  principled way to decide which rules to disable versus which findings
  are acceptable
* A relaxed rule set stays relaxed for new code too, not just the old code
  that motivated the exception

| Verdict
| Rejected. The baseline mechanism exists specifically to solve "adopt a
  linter on an existing codebase" without this tradeoff.
|===

=== Detekt's `formatting` rule set in addition to `ktlint`

[cols="1,4"]
|===
| Criterion | Assessment

| Strengths
a|
* One fewer tool conceptually, if it fully replaced `ktlint`

| Weaknesses
a|
* Directly overlaps with Spotless's existing `ktlint` integration; running
  both risks contradictory formatting demands from two tools
* Replacing `ktlint` with Detekt's `formatting` rule set instead would
  require re-litigating and possibly rewriting `spotless.gradle.kts`,
  disproportionate to this task's scope

| Verdict
| Rejected. Keep formatting solely owned by Spotless/`ktlint`; Detekt
  covers the rest.
|===

=== No second static-analysis tool; Spotless/`ktlint` alone is "the deliberately chosen combination"

[cols="1,4"]
|===
| Criterion | Assessment

| Strengths
a|
* Zero new tooling, config, or CI time
* `ktlint` already catches some structural issues incidentally

| Weaknesses
a|
* `ktlint` is a formatter, not a code-smell/complexity analyzer; it has no
  concept of, e.g., cyclomatic complexity, long methods, or several
  Kotlin-specific anti-patterns Detekt's default rule sets do check
* Leaves the task's own premise ("a consistent static-analysis policy")
  unaddressed beyond what already existed before this task

| Verdict
| Rejected. Formatting and static analysis are different concerns; the
  project had only ever addressed the former.
|===
